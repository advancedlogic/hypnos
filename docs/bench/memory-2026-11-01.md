# Booked vs real memory per model (TEST-3), Apple Silicon, 2026-11-01

Machine: MacBook Pro M5 Max, 128 GB unified memory, macOS 27, Metal build at commit after
`f023b2b`. Tool: `hypnos measure-memory <config> [--models ...] --out <file>` loads each model alone
(every other model evicted first), runs one request of its kind (a chat of ~600 prompt tokens +
64; an image for a model that sees; the 11 s `jfk.wav` for one that hears; 8 embeddings; one
spoken sentence; one 1024x1024 image in 4 steps; entities over ~600 tokens; docling is loaded
only), and samples every 50 ms the process footprint and the device memory Metal reports in use.
"Real" is the growth of the device reading for GPU models (the weights are memory-mapped files,
so they hardly show in the footprint) and of the footprint for CPU models. "Booked" is the
placement the scheduler committed: GPU weights + KV + workspace, or host RAM for a CPU model.
Configs: `hypnos.macos.example.toml`, `hypnos.lfm3.macos.example.toml`.

Under-booking (real above booked) is the dangerous direction: the planner admits a model the
device cannot hold. Every llama.cpp model with a vision or audio encoder was under-booked, MOSS
by 2.5 GiB at its largest image size, and the KV caches were over-booked at the same time.

## What was wrong

- **KV layout.** The formula booked every layer at the largest KV head count and head size, at
  the full context unless one global layer came every N. Gemma 4 26B's global layers have 2 KV
  heads x 512 and its 25 sliding-window layers 8 x 256; LFM3 has 6 full-attention and 5
  sliding-window layers of 4 x 128 and 13 convolution layers with no KV cache at all (it was
  booked as 24 full-attention layers). llama.cpp also sizes a sliding-window cache as the window
  plus one micro-batch (2048 tokens with a projector, 512 without), padded to 256 cells.
  Detection now reads the per-layer KV heads and the sliding-window pattern from the GGUF into
  `global_kv_layers`, `global_num_kv_heads`, `swa_kv_layers`, `swa_num_kv_heads`,
  `swa_head_dim`, and `kv_bytes_for_layers` books exactly that.
- **Working memory.** The encoders' and the diffusion model's compute buffers were above
  `activation_workspace_bytes`. The new values are the measured peak minus weights and KV, plus
  0.25 GiB: 26B 2.75 GiB, E4B 1.25 GiB, LFM3-VL 1.75 GiB, LFM3-Audio 1.5 GiB, MOSS-Image 5.75 GiB.
- **Kokoro** runs on the CPU (ONNX Runtime with PreferCPU) but was booked in GPU memory: it is
  `device = "cpu"` now and booked in RAM.

## Not measured

- **CUDA.** These are Metal numbers. The CUDA profile got the same working-memory floors (a
  CUDA build's compute buffers are not smaller), but nobody has run `measure-memory` on a CUDA
  machine yet; device memory there comes from the GPU probe, so the tool works unchanged.
- **Long contexts and several slots.** KV is allocated when the context is created, so its full
  size is in these numbers; compute buffers at the default micro-batch are too. A request that
  fills 16k tokens of context was not run.

## Watching for drift

`/metrics` exports `hypnos_memory_bytes{kind="booked"|"footprint"|"held"}` next to
`hypnos_vram_bytes{kind="unaccounted"}` (device memory in use beyond the bookings). An alert on
held well above booked (or unaccounted growing) means some engine needs more than its booking
says: run `hypnos measure-memory --models <id>` and raise that model's `activation_workspace_bytes`.
