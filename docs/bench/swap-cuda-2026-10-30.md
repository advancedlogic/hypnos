# Tier 2 -> Tier 1 promotion on CUDA (2026-10-30)

PERF-6: the first chat after startup promoted `gemma4:26b-q4` (15.8 GB of weights, 1.2 GB vision
projector) from pinned RAM into VRAM in 23 s, and the chat after an image generation in 59 s, on a
machine where the same promotion takes 0.99 s from Tier 2 on an M5 Max
([swap-metal-2026-10-29.md](swap-metal-2026-10-29.md)). This is where the time went and what
changed.

## Setup

- Laptop with an RTX 5090 Laptop GPU (24 GB), 63 GB of RAM, NVMe, Windows 11, driver 591.91,
  CUDA 12.8 build with `--features docling-cuda`.
- Default lineup (`hypnos.example.toml`): `gemma4:26b-q4` and `gemma4:e4b-q4` pre-staged in Tier
  2, `slots = 4`, `default_context_len = 16384`; Tier 2 budget 32 GiB.
- Promotion = `POST /v1/memory/tier` to `tier2_pinned_ram`, then to `tier1_gpu_vram`, wall time
  of the second call; "after image" = one 512 x 512 MOSS-Image generation (which evicts the 26B
  from VRAM) followed by the promotion. Phases from the new `Tier 1 load phases` log line, also
  in `hypnos_telemetry.tier_switch_phases`.

## Where the time went

The switch had no breakdown, so the first change was to time it: weights (llama.cpp load incl.
the GPU upload), projector (libmtmd), context (KV cache for `slots x n_ctx` and compute buffers).

| State of the code | Promotion, warm | Weights | Projector | Context | After an image |
| :--- | ---: | ---: | ---: | ---: | ---: |
| before (mmap, projector not pinned) | 7.3-7.6 s | 6.4-6.6 s | 0.75 s | 0.3 s | 10.9 s (projector 6.9 s, context 1.2 s) |
| weights read through pinned buffers | 3.8-4.1 s | 2.7-3.0 s | 0.75 s | 0.3-0.4 s | 10.9 s (projector 6.9 s, context 1.2 s) |
| + projector and text encoders pinned in Tier 2 | 3.7-4.1 s | 2.6-3.0 s | 0.7 s | 0.35 s | 6.6 s, image request 144 s (see below) |
| + MOSS-Image no longer kept warm | 3.7-4.2 s | 2.6-3.1 s | 0.7 s | 0.35 s | **3.7 s**, image request 11 s |

Tier 3 -> Tier 1 (weights unpinned, OS page cache still warm): 8.3 s before, 4.6 s after.

1. **Mapping the file is the slow way to feed CUDA on Windows.** With `use_mmap = true`
   llama.cpp copies each tensor from the mapping through pageable memory, 658 tensors at about
   2.4 GB/s. With the file read instead, llama.cpp streams it through four pinned 1 MiB staging
   buffers with asynchronous uploads, about 5.5 GB/s here: the weight phase goes from 6.5 s to
   2.7 s. The default is now `read` whenever layers go to a CUDA device; `use_mmap = true` per
   model brings the mapping back (it stays the default on Metal, where the mapping is the
   model's memory, and for CPU placements).
2. **Only the main weights file was pinned.** Tier 2 locked `weights_path` and nothing else, so
   the 1.2 GB projector (and MOSS-Image's 5.7 GB text encoder) lived in the OS page cache and was
   evicted by the next big load: the projector phase went from 0.75 s to 4-7.5 s whenever another
   model had been loaded in between, which is what the 23 s and 59 s first chats were. Tier 2
   now pins the `aux_weights_path` and `text_encoder_path` files with the weights; the booking
   already counted them (`total_weight_bytes`), the lock just did not.
3. **Locking what is booked made the budget real.** With every file pinned, the 32 GiB Tier 2
   budget was actually held (31.8 GB locked: both chat models with projectors, plus MOSS-Image's
   9 GB after `keep_warm_in_ram`) next to the process's own 23 GB on a 63 GB machine. Free RAM
   fell to 3.7 GB, the OS paged at 300k pages/s, and evicting the 26B into Tier 2 under that
   pressure took 134 s (the "144 s image request": sd.cpp's own load was 0.9 s). MOSS-Image gains
   nothing from Tier 2 (sd.cpp reloads it from the page cache in about a second), so the example
   profiles no longer keep it warm, Tier 2 settles at 22.5 GB and free RAM at 20 GB. The memory
   manager now warns at startup when `pinned_ram_budget_bytes` exceeds half of physical RAM.

## What is left

- 2.7 s for 15.8 GB is 5.5-5.9 GB/s, about half of what PCIe 4 x8 should move; llama.cpp's
  loader uses 1 MiB staging chunks, and `LLAMA_LOAD_MODE_DIRECT_IO` (unbuffered reads, larger
  buffers) is worth a try for Tier 3 loads. The Metal number (0.99 s) is unified memory: no copy.
- Context creation is 0.35 s warm but 1.2-2.2 s right after another model's unload (VRAM
  allocation after large frees); not pursued.
- PERF-5 still wants the full `bench.sh --scenarios 7` chart on CUDA next to the Metal one.

## Reproducing

```bash
# promote three times and print the phases of each load
for i in 1 2 3; do
  curl -s -X POST localhost:8080/v1/memory/tier -H 'Content-Type: application/json' -d '{"model":"gemma4:26b-q4","target_tier":"tier2_pinned_ram"}' >/dev/null
  curl -s -o /dev/null -w 'promotion %{time_total}s\n' -X POST localhost:8080/v1/memory/tier -H 'Content-Type: application/json' -d '{"model":"gemma4:26b-q4","target_tier":"tier1_gpu_vram"}'
  grep -a 'Tier 1 load phases' .run/backend.log | tail -1
done
# the same phases arrive with a request that loads the model: hypnos_telemetry.tier_switch_phases
```
